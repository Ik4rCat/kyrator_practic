# Список спорных решений — «Курсатор»

## 1. Пользователи: кэшировать права в Redis с TTL vs всегда читать из PostgreSQL

**Аргументы за кэш в Redis:** проверка прав происходит на каждом запросе, читать её каждый раз из PostgreSQL — лишняя нагрузка на основную базу; TTL 5 минут держит компромисс между нагрузкой и актуальностью.

**Аргументы за чтение напрямую из PostgreSQL:** права — критичные данные, задержка обновления (лаг) при отзыве доступа — риск безопасности.

**Решение:** кэшируем с TTL 5 минут + принудительное удаление ключа при смене роли; для критичных действий (удаление курса, выплаты) права читаются напрямую из PostgreSQL, минуя кэш.

---

## 2. Сессии и токены: серверное хранение в Redis vs stateless JWT

**Аргументы за Redis:** можно мгновенно отозвать сессию (разлогинить пользователя принудительно), встроенный TTL.

**Аргументы за JWT:** не нужно отдельное хранилище, меньше инфраструктуры.

**Решение:** Redis — потому что мгновенный отзыв сессии важнее экономии на инфраструктуре.

---

## 3. Курсы и уроки: единая база (PostgreSQL, EAV-схема) vs разделение на PostgreSQL + MongoDB

**Аргументы за единую базу:** один источник истины, не нужна синхронизация.

**Аргументы за разделение:** метаданные курса нуждаются в целостности и связях (FK), а тело курса имеет разную вложенную структуру у разных курсов — в реляционной схеме это выродилось бы в неудобную EAV-модель.

**Решение:** разделили — метаданные в PostgreSQL, контент в MongoDB, синхронизация через transactional outbox. Цена решения — дополнительная сложность и риск рассинхронизации при обновлении.

---

## 4. Прогресс по курсам: только Redis vs только PostgreSQL vs оба

**Аргументы за только Redis:** максимальная скорость чтения текущего состояния.

**Аргументы за только PostgreSQL:** надёжное хранение истории и результатов, но медленнее при большом числе пользователей.

**Решение:** PostgreSQL как источник истины (транзакционность нужна для зачёта и сертификата) + Redis как write-through кэш текущего состояния + ClickHouse для истории событий.

---

## 5. Поиск по курсам: PostgreSQL full-text search vs Elasticsearch

**Аргументы за PostgreSQL FTS:** не нужна отдельная инфраструктура, встроенные триграммы под опечатки, для среднего объёма достаточно.

**Аргументы за Elasticsearch:** специализированный инвертированный индекс, лучше справляется со сложным ранжированием при росте числа курсов.

**Решение:** Elasticsearch — заложились на рост объёма и необходимость сложного ранжирования.

---

## 6. Форум / обсуждения: дерево ответов в PostgreSQL (ltree/CTE) vs документ в MongoDB

**Аргументы за PostgreSQL:** удобно считать лайки и вести модерацию с аудитом и целостностью.

**Аргументы за MongoDB:** удобно хранить всю ветку обсуждения одним документом при вложенных ответах.

**Решение:** PostgreSQL — модерация и целостность важнее, но признаём: при большом объёме вложенности MongoDB могла бы упростить чтение целой ветки.

---

## 7. Логи действий: прямая запись в ClickHouse vs буфер (Kafka / Redis Streams) перед ClickHouse

**Аргументы за прямую запись:** меньше инфраструктуры на старте проекта.

**Аргументы за буфер:** сглаживает пиковую нагрузку, не теряет события при кратковременной недоступности ClickHouse, батчирует вставки.

**Решение:** заложили буфер (Kafka или Redis Streams) с самого начала, поток событий изначально может быть неравномерным.

---

## 8. Аналитика и отчёты: считать витрины в реальном времени vs материализованные представления по расписанию

**Аргументы за реальное время:** всегда свежие данные.

**Аргументы за расписание (cron 15 мин):** тяжёлые агрегаты не нагружают систему постоянно, а считаются пакетом.

**Решение:** материализованные представления, cron раз в 15 минут — свежесть T+15 мин признана приемлемой ценой за экономию ресурсов.

---

## 9. Рекомендации курсов: расчёт в ClickHouse vs выделенная графовая БД (Neo4j)

**Аргументы за ClickHouse:** матрица «пользователь × курс» уже там лежит, не нужна новая система.

**Аргументы за Neo4j:** для сложных коллаборативных фильтров графовая база или отдельный сервис рекомендаций работает нативнее.

**Решение:** пока ClickHouse (батчевый расчёт раз в сутки + выдача из Redis), с открытым вопросом перехода на Neo4j при усложнении алгоритмов.
